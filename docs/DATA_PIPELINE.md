# Обновление каталога Москвы

Рабочая база — Supabase HramGo. Публичный сайт читает статический снимок, который формируется через read-only RLS; обновление базы становится видимым после сборки и публикации.

## Команды

Нужна `SUPABASE_DATABASE_URL` в `.env.local`, SSL verify-full и официальный сертификат. Серверный ключ браузеру и GitHub Pages не передаётся.

```powershell
npm run temples:update -- --inventory
npm run temples:update -- --dry-run
npm run temples:update -- --apply
npm run temples:update -- --apply --resume
npm run temples:update -- --only-missing-schedules --apply
npm run temples:update -- --only-stale --apply
npm run temples:update -- --temple=<slug> --dry-run
node --env-file=.env.local scripts/catalog-report.mjs
node --env-file=.env.local scripts/sync-catalog.mjs
```

Без `--apply` изменения в базу не записываются. Контрольная точка содержит старое/новое значение, источник и результаты извлечения. `--from-checkpoint=<file>` повторно разбирает сохранённые источники исправленным парсером без сетевого обхода. `--force` предназначен для явного повторного обхода; обычный запуск исключает недавно проверенные объекты.

## Источники и экономия запросов

Перед изменениями создаётся приватная копия девяти таблиц каталога в `tmp/backups/`. `.cache/hramgo/` содержит очередь, контрольные точки, HTML, файлы, ETag, Last-Modified, SHA-256 и результаты извлечения текста. Эти каталоги исключены из Git.

Шесть работников, максимум восемь; HTTP timeout 12 секунд, максимум три попытки только при временных ошибках. Robots.txt учитывается. Редиректы ограничены; приватные адреса и URL с паролями не допускаются. Один URL загружается один раз за запуск, повторные запросы условные. Файлы ограничены 8 МиБ. Прогресс фиксируется пакетами по 25 объектов; SQL-транзакции записывают только отличающиеся данные.

Недоступные источники повторно проверяются не раньше суток; отсутствующее расписание — через семь дней, подтверждённое — через 30. Адреса, историю и контакты не нужно проверять каждую неделю. В этом проходе использованы ранее сохранённые карточки официального справочника, а не повторный обход всех 757 карточек.

## Публикация расписаний

Датированные HTML-таблицы требуют явных даты, года и сопоставления времени со службой. Регулярные записи хранятся отдельно, без вымышленного периода действия. Несколько неопределённых времён, исключения, открытие храма, даты без года, неоднозначные виды служб и общие сайты разных объектов требуют проверки.

PDF сначала читается pypdf; DOCX — стандартным XML parser. Windows OCR читает изображения на русском языке; текст и hash сохраняются. Порядок колонок OCR и PDF может не соответствовать порядку служб, поэтому такие кандидаты не публикуются автоматически. Проверенные вручную записи находятся в `data/reviewed-schedule-entries.json`, вместе с hash источника. Изменившийся источник требует повторной проверки; старые подтверждения парсера переводятся в REVIEW. Поиск показывает только VERIFIED с confidence ≥ 0.8 и проверкой не старше 30 дней.

Готовый отчёт: `data/catalog-update-report.json`; очередь проблем: `data/catalog-issues.json`. `NO_SCHEDULE` означает отсутствие подтверждённого расписания, а не доказательство отсутствия служб. Общие монастырские расписания сопоставляются с конкретными храмами; комплекс указан в описании и поле `scope_note`.

## Фотографии и оставшиеся пробелы

В Storage загружаются только изображения с установленной лицензией/разрешением. Новые фотографии с неизвестными правами не копируются. Существующие внешние фото нуждаются в дальнейшей проверке прав и соответствия объекту. Неточные координаты не заменяются центром Москвы или центром монастыря. Для добавленных храмов Данилова монастыря координаты оставлены пустыми до проверки отдельных зданий.

Кандидаты дубликатов с одинаковой точкой требуют проверки: разные храмы и часовни одного комплекса могут иметь общую координату. Три подтверждённых дубля монастырей объединены с сохранением исходных URL страниц; журнал — `data/reviewed-temple-merges.json`.

## Транспорт и контрольная выборка

`node --env-file=.env.local scripts/refresh-transit.mjs --apply` обновляет ближайшие станции для объектов с координатами. Геоданные — публичный справочник HeadHunter; источник и hash сохраняются. Учитываются метро, МЦК и МЦД-1–4. Открытие первого участка Рублёво-Архангельской линии подтверждено [Московским транспортом](https://transport.mos.ru/mostrans/all_news/131519), состав Троицкой линии — [сообщением об открытии](https://transport.mos.ru/mostrans/all_news/126335). Старый перечень Каховской линии исключён из расчёта.

Расстояния вычислены по прямой; время пешком — приблизительная оценка, без проверки реального пешеходного маршрута. Независимо проверенные маршруты сохраняются. Отчёт: `data/transit-refresh-report.json`.

`node --env-file=.env.local scripts/revalidate-cached-schedules.mjs --apply` перепроверяет только уже сохранённые HTML-источники расписаний, без HTTP-запросов. Проверка не повышает неподтверждённые записи до VERIFIED. Конфликт дня недели с датой, часы открытия храма, причащение в ориентировочное время и расписание приписного храма требуют исключения или отдельного сопоставления.

По просьбе владельца восстановлен исходный интерфейс: голубая палитра, стеклянные панели, каталог с фильтрами слева, прежние карточки и сворачиваемые разделы страницы храма. Вход, избранное и отзывы отсутствуют. В блоке расписания показываются подтверждённые службы ближайшей недели, источник, дата проверки и конкретное здание комплекса; справочные неподтверждённые сведения отделены.

Монастырь представлен одной карточкой: его внутренние храмы хранятся в details.includedTemples, их названия — в aliases, старые URL — в mergedSlugs. Внешние подворья по другому адресу остаются отдельными объектами. Для Данилова монастыря 5 внутренних карточек объединены; источник и название конкретного здания сохранены на службах. Скрипт add-reviewed-temples использует эту же модель и не создаёт их заново. Карта восстановлена на Яндекс API 2.1, обозначения метро показывают название станции без расстояния.
